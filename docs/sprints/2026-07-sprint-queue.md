## The diagnosis in one paragraph

The repo contains **three coexisting generation pipelines**: (1) the legacy daily slot-filler
(`exercise_pool` + two-pass `plan_generator`) that everyone's live plans still come from,
(2) Program Builder v1's rotation-repeat scheduler + `program_aware_planner` projection
(live behind `program_aware_plan_gen` for all 12 pitchers), and (3) Program Engine v1
(LLM-forward author + guardrails + projection + governor) — built on PR #34, dormant behind
`PROGRAM_ENGINE_V1=False`, its LLM path never run against a real model. The slop is not one
bad function; it's the coexistence: two program tables, two phase vocabularies, three answers
to "who authors today's plan." The endgame is **one spine**: engine authors the program →
projection produces the day → the legacy slot-filler survives only as the deterministic
fallback floor.

## The generation constitution (draft — Landon ratifies in Sprint B)

The "weights of LLM vs deterministic" question, answered as a division of authority rather
than a dial:

| Plane | Authority | Runs |
|---|---|---|
| **LLM (research-grounded)** | Program *authoring*: phase structure, week-by-week progression, exercise selection, intent, the "why" — reasoning over player context + goal + retrieved knowledge docs | Once per program (compile time, latency-tolerant), and on explicit regenerate |
| **Deterministic** | Everything safety- and math-shaped: ACWR/load math, contraindications, deload cadence, monotonic ramps, pull:push, exercise-ID resolution, day *projection* within program bounds, triage | Every day, every check-in — repeatable, testable, no model variance |
| **Authored knowledge (docs/templates/golden programs)** | The tunable content both planes read: edit a doc → next generation changes, no code change | Resolved at generation time |

Rule of thumb: **the LLM decides *what the program is*; determinism decides *whether it's
safe* and *what today is*.** Day-to-day output must never depend on a live LLM call
succeeding (the two-pass lesson, kept).
